# Product facet engine — real filters over sparse supplier data

Use when a shop/catalogue (PHP+SQLite, OpenCart, Medusa, static HTML) needs **real filters**, but:
* the client says "make the filter like *<big distributor>*" (they mean spec facets with counts,
  selected-filter chips, multi-select, show-more), or
* the supplier feed ships little or no technical data (typical for ERP/Icecat-style CSVs: name, EAN,
  weight, price and nothing else), or
* sub-categories, attribute values or delivery weights simply do not exist in the feed.

Hard rule for every value you show: it must trace to feed data or to a **name-derived extraction**.
Never invent a spec value, a count or a price. Unknown → omit the facet, or show "on request".

## 1. Decide where each filter comes from

| Source | Examples | Notes |
| --- | --- | --- |
| Feed properties | `product_properties(name,value)` from XML feeds | Richest, use first. |
| Name-derived | Colour, Capacity, Memory type, Interface, Screen size, Wi-Fi, Ports, Power, Length | Works for feeds with zero properties — see §3. |
| Structural | brand, category, sub-category, price range, "has photo" | Always available. |
| Weight | `products.weight` (kg) | Drives delivery pricing, not a facet. |

One feed often has properties and the other has none: extract only for products whose feed lacks them
so you never overwrite real supplier values.

## 2. Sub-categories when the feed has no sub-level

Ordered rule table, first match wins, applied **at import time** (`inc/taxonomy.php` →
`catalogue_subcategory_rules()`: category name → `[[sub_name, regex], …]`). Key the table on the exact
category name after any "clean split" mapping — a case difference (`Junction boxes` vs `Junction Boxes`)
silently yields zero matches, so dump the real category names and diff them against the rule keys.

* Unmatched products stay `subcategory_id = NULL` — do **not** funnel them into an "Other" bucket.
* Slugs are generated by the importer; the same code path then serves sub-category pages, facets,
  breadcrumbs and the sitemap for free.
* Realistic outcome: 195 feed-provided sub-categories → 365 after derivation, 76 % of 38 k products placed.
* UI visibility matters as much as the data: a chip strip with counts at the top of the category page,
  a "Categories in <department>" index on the department page. **This user wants only the main
  categories on the department index (no sub-links there) and the full sub-category strip on the
  category page** — don't duplicate the same list in the sidebar as well.

## 3. Derive attributes from product names, store them as real properties

The whole trick: write the derived values into `product_properties` at import, so the facet engine, the
filter SQL, the sitemap and the spec table all work with **one** mechanism instead of a parallel
"derived" code path.

* Use `sort = 1200` (or any high value) for derived rows, and skip a name the feed already provided.
* Rules live in one file (`inc/attributes.php` → `extract_attributes($name, $category)`), returning
  `['Interface' => 'HDMI', …]` — only attributes actually found.
* Bounded numerics and explicit suffixes are the difference between a useful facet and noise:
  * speed requires `Gbit|Gbps|GbE|igabit` **and** 1–400 → otherwise "4G/5G" LTE routers become "4 Gbit";
  * screen size bound 10–120 inch, wattage 45–4000 W, cable length 0.1–100 m;
  * `Paper size` only when the name also mentions paper/print/photo/label (else `A3` from a part number leaks in);
  * normalise `1024 GB → 1 TB`, `gray → Grey`, `802.11ax → Wi-Fi 6`, join two colours as `Black / White`.
* Keep the false positives out of the facet by discarding groups that are not discriminators (§4).
* Full rule catalogue and parser gotchas: `references/derived-attributes-from-names.md`.

## 4. Facet discovery engine

One **shared scope builder** feeds both the listing query and the facet queries — duplicating the
joins/WHERE is how listing counts and facet counts drift apart.

```php
function scope_sql(array $f, bool $withSpec = true): array   // [from, whereSql, params, joinFts]
```

Discovery, per request:
1. Top candidate property names in this scope: `SELECT pp.name, COUNT(DISTINCT pp.product_id) cov …
   GROUP BY pp.name HAVING cov >= 3 ORDER BY cov DESC LIMIT 40`, minus a **blacklist**
   (`Vendor_url`, `Dimensions`, `Weight`, `EAN`, `Part number`, `Warranty`, `Model`, `Other`, …).
2. Per name, fetch its top ~26 values with counts.
3. Keep a name only if it has 2–24 values, at least 8 products, and its top value covers ≤ 85 % of the
   group (a value that covers everything is not a discriminator).
4. Order the groups by an explicit **priority list** (hardware specs first, `Colour` last) instead of raw
   coverage — coverage alone happily shows `Audio` and `Pen` ahead of `Screen size`.
5. Take ~6 groups × 8 values.

Filtering: one `EXISTS` per property group (AND between groups, OR within a group), params appended in
order:
```sql
EXISTS (SELECT 1 FROM product_properties x WHERE x.product_id = p.id AND x.name = ? AND x.value IN (?,?))
```
Index it: `CREATE INDEX idx_pp_name_value ON product_properties(name, value)`.

Cache the facet aggregates in a file cache keyed `md5(scope) + built_at` with a 1 h TTL — cold ≈ 230 ms,
warm ≈ 30–40 ms. **The `built_at` meta must be part of the key**, otherwise a re-import leaves stale
counts on screen for an hour. Prune cache files older than ~7 days on write.

## 5. Filter UI and URL contract

* Multi-select, not radio: `?brand[]=hp&brand[]=lenovo` (and `?spec[Screen size][]=27 inch`), so the
  filter query takes an array per group; the sort/per-page forms must re-emit array params as hidden
  inputs or sorting silently drops the filters.
* **Selected-filter chips** above the results, each with an ✕ that removes exactly that value
  (`url_without_value($key,$value)`, `url_without_spec($name,$value)`) plus "Clear all".
* **Exactly one button in the sidebar — labelled `Filter`.** No "Filters" heading text beside it, no
  Show/Hide panel toggle, no per-group "Show N more": the owner removed all of them explicitly. Long
  value lists scroll inside their own box (`max-height` + `overflow-y:auto`, `.fopts-scroll`); the button
  stays compact (`~72×37 px`, `btn-sm`, `width:auto` — not full-width on desktop *or* phone) and carries
  the active-filter count as a small badge. On phones that one button opens / closes the (collapsed)
  list — filters apply as you tick, so there is no "Apply" step.
* Per group: selected count badge and right-aligned counts. Per page: 24/48/96.
* Filtered/paginated URLs: `noindex, follow` + canonical to the clean URL (unchanged from the feed-site
  baseline).
* When the owner forces "everything is available", **remove the availability facet** — a filter whose
  single bucket equals the total is noise.

### 5a. Filtering must not reload the page (and counts update in place)

Owner requirement in plain words: *"clicking a filter must not reload the page, so I can add several
filters at once"*. Working PHP + JS recipe, JSON contract and test method:
`references/ajax-facet-refresh.md`.

* One JSON fragment endpoint serves every listing route (`…?<filters>&frag=1` → `{results, counts, total,
  url, title}`); the page view and the fragment endpoint both build their state through **one shared
  `listing_context()`**, otherwise the page and the fragments drift apart.
* **Refresh the results, never the sidebar HTML.** Re-rendering the sidebar under the cursor *is* the
  owner's complaint *"I tick one filter and a different one gets marked"* — the list re-orders around the
  click. Replace only the results block and patch the sidebar **in place** (count text + hide/show items):
  the ticked box stays the same DOM node, checked, where the finger left it.
* **Live counts, zero values gone.** Count each group with every other filter applied and *its own
  selection relaxed* (`facet_live_counts()`), hide values whose count is 0 unless they are ticked, and hide
  the whole group when nothing is left in it. Force-inject the ticked values into the value list — top-N
  facets would otherwise drop them and the shopper could not untick. Compute this only when a filter is
  active: with no selection the cached scope scan gives the same numbers far cheaper (measured here: 17 ms
  unfiltered page, 49 ms filtered page, 53 ms fragment).
* `history.pushState` on every change plus `popstate` for the back button; reset `page` to 1 on a
  filter/sort change but **keep** it for pagination and per-page links; reuse the browser's own query
  string for the clean URL (dropping `frag` and the default sort, skipping empty `min=`/`max=`) rather than
  re-serialising with `http_build_query`, which rewrites `spec[Socket][]=LGA1700` into
  `spec[Socket][0]=LGA1700`.
* Progressive enhancement is not optional: the same form still performs a normal GET without JS, so one
  test must `curl` exactly the query the form would send.

## 6. Weight-driven delivery pricing (same dataset, same honesty rule)

Delivery cost is a catalogue feature: compute it from real product weights and **published carrier
rates**, never from a guess.

**Weight can be missing for a whole feed.** The XML feed had no weight column at all, so 5 400 products
would have shipped on an "estimated 0.5 kg". Lift the value out of the feed's own properties at import
instead: `Weight: "1.70 kg"`, `"Starting at 1.38 kg"`, `"450 g"` → `products.weight` (parser = first
number + unit, `g` → /1000, bound 0–200 kg, written only where the column is empty). 1 713 products
gained a real weight that way and the delivery band stopped being an estimate. Never guess a weight —
an unknown stays unknown and the summary says so. Bulgaria (Speedy operates the DPD network there; `www.dpd.bg` redirects to
speedy.bg), official price list, service codes, per-country group prices and the fetch recipe are in
`references/bg-carrier-tariffs.md`. Destinations outside the published tariff → "price on request".

## 7. Filling data holes without inventing them (the same honesty rule)

Whatever the hole — facets, weights, photos — the answer is *derive from real data, label the estimate, or
show nothing*.

* **Photos:** one feed can ship zero image data (empty `Images` column for every row, no URL anywhere in
  the file — check before promising). Then: reuse the photo of the feed that *has* them **only** for the
  same normalized part number (variant rows like `/EXP` or `GIFT` are the same physical item — 242 of
  38 k in practice), replace the rest with a *designed* placeholder (inline-SVG line-art glyph per
  department + brand + part number, ~20 glyphs covering 24 departments) instead of a grey "no photo" box,
  keep one honest line on the product page ("manufacturer publishes no photo — ask us"), and tell the owner
  what a real image feed would need. Never scrape a competitor or borrow an unrelated brand photo.
* **Weights:** lift them out of the feed's own property strings before falling back to an estimate (§6);
  an estimate that reaches the customer's total must be labelled as one.
* **Attributes/sub-categories:** name-derived rules (§2/§3) beat an empty filter panel — but a value that
  cannot be traced back to the feed or to the product name stays out.

## 8. Owner-request patterns seen on reseller catalogues

* **"All products must be available."** Do not rewrite the feed data. Keep the real availability in the DB
  and add one config flag (`force_availability = 'in_stock'`) that the display layer, the JSON-LD
  (`InStock`), the facet counts and the availability filter all read — reversible in one line. Remove the
  now-meaningless availability facet, and soften any sentence that claimed local stock
  ("Available to order — lead time confirmed with the order").
* **"Make it an order page, not an enquiry."** Then deliver a real checkout: order summary with totals,
  the delivery price, a **Place order** button, an order reference (`ERP-2026-00001` from the row
  sequence) shown in the confirmation, and totals/weight recomputed server-side from the product slug on
  POST. Keep the enquiry/quote flow on its own page — this user's standing preference is that a new
  function gets **its own URL with its own SEO**, never a section bolted onto an existing page.
* **Conditional required fields (business vs private).** Star the always-required fields; wrap
  type-dependent ones in `[data-business-only]` and toggle both `hidden` and `required` in JS — then
  **re-validate the same rule server-side**, because a hidden `required` input is simply not submitted.
  Blank out data that does not apply to the chosen type before storing.
* **Prices must be shown with and without VAT, and the type picks the mode.** Private customer: goods,
  delivery and total **incl. VAT**. Business / reseller: the same three lines **excl. VAT** (carrier
  prices are published VAT-inclusive, so delivery net = gross / 1.2). Rates by destination: local VAT in
  BG; 0 % intra-community once a VAT number is given (VIES); the destination standard rate for an EU
  private buyer; 0 % export outside the EU — plus a line that the invoice is the authoritative document.
  Keep the detailed breakdown in one box and a compact 3-line total directly above the submit button.
* **Copy hygiene — this owner prunes anything supplier-facing from the customer UI.** Removed on request
  across sessions: the top banner, the note under the delivery options, the footer disclaimer pair
  ("Product data is updated automatically from our supplier catalogues (last import …)" / "Product names
  and brands are the property of their respective owners…"), the "pickup / own carrier at our premises"
  option, and the product-page line `Second supplier price: 111.17 € net`. Ship prices, labels and fields;
  put explanations on FAQ/static pages. When a price/field leaves the UI, also delete the now-dead CSS
  class and the unused variable, and keep the DB column (so it can come back in one line). Customer-facing
  carrier brand here is **DPD**; provenance comments live in code, never in the page.
* **Wide price/facet tables must survive a phone.** With 10+ columns, switch to stacked cards at
  `≤760px`: hide `thead`, `display: block` on rows, `data-label` on every cell and
  `td::before { content: attr(data-label) }`. Verify with the CDP check (see `scripts/`), not by eye.
* **Never a price, weight or lead time that is not sourced.** Unknown → "on request", confirmed by the
  owner; this user rejects invented numbers outright and checks the site live right after delivery.

## Pitfalls

* **A column that does not exist in a shared `SELECT` constant takes the live site to 500.** Real case:
  `p.weight_kg` while the schema column was `weight` — every listing page returned 500 until fixed.
  Check `.schema` first, alias in the constant (`p.weight AS weight_kg`), and after touching a shared
  query constant/helper re-sweep every route type (`curl` per route, assert 200 + no `Warning:`/`Fatal`).
* **PHP: two string literals on consecutive lines is a parse error.** Long FAQ/array strings need an
  explicit `.` concatenation; `php -l` catches it only if you actually lint (`for f in $(find . -name
  '*.php'); do php -l $f; done`).
* **`[$a, $b] = $assocRow` silently yields `null`s.** Destructuring an associative array produces empty
  table cells / missing rows with no error. Use named keys (`$row['service']`). Symptom to remember:
  table headers render, body rows are empty.
* Derived attributes must not overwrite feed-provided properties; log how many rows you skipped.
* Facet counts must be computed with the same scope builder as the listing, and cached on `built_at`.
* Do not add a second entry point for "derived" filters — write them into the existing properties table.
* **A scripted "replace all" edit can duplicate an array key.** Inserting the same block into two PHP
  functions (`shipping_services()` and `shipping_rates()` both start with `'cee202' => [`) put a service
  definition where a price array belonged; PHP silently keeps the **last** key, so the option rendered as
  "on request" with no error anywhere. After editing data tables with `str.replace(..., -1)`, assert the
  shape back (`php -r 'print_r(array_keys(...))'`) and unit-print one country's quote.
* **Verify multi-step flows from a script file, not a long inline one-liner.** Complex chained commands
  get refused by the shell guard; write `verify_<area>.sh` / `<area>_flow_test.sh` next to the site
  tooling, `bash` it, and keep the reusable ones in the skill's `scripts/`.
* **A `Secure` session cookie makes local-HTTP testing look broken.** Behind Cloudflare the app sees
  `X-Forwarded-Proto: https`, so PHP sets the session cookie `Secure`; a `curl http://127.0.0.1:8080`
  test then never sends it back, CSRF tokens never match and every account action returns `err=csrf`.
  Run cookie/account flow tests against the **public HTTPS origin**, and keep the local vhost for
  anonymous page sweeps. Details: skill `customer-accounts-and-sessions`.
* **An inline `onchange="this.form.submit()"` kills the no-reload behaviour.** `form.submit()` fires no
  `submit` event, so a listener that preventDefaults the submit never sees it and the page reloads anyway
  (symptom: sort/per-page "work" but the whole page jumps). Drop the inline handler, hook the `change`
  event on the select (`[data-sort]`) and add a `<noscript>` submit button for the JS-off case.
* **A JSON fragment view must never be wrapped in the page layout.** `render()` requires the view and then
  `views/layout.php`; the fragment therefore came back as a full HTML document with the JSON buried in it
  (right `Content-Type`, unparseable body). Every route signature stays the same — branch inside the
  renderer: `if (str_starts_with($view, 'api_')) { echo $content; return; }`.
* **`PRAGMA query_only = ON` on the read connection makes every CLI write fail.** The app's `db()` is a
  hardened read-only handle, so a maintenance script reusing `qexec()` dies with
  `SQLSTATE[HY000]: General error: 8 attempt to write a readonly database` while the web path (which opens
  its own write handle) is fine. Give the write path its own connection (`db_open_rw()` behind a
  `db_write()` helper) and route admin/CLI updates through it.
* **A shared context helper + `extract($arr, EXTR_SKIP)` leaves the caller's `$CTX` stale.** The helper
  receives `$CTX` by value, enriches its own copy (filters/result/facets) and returns it; `EXTR_SKIP` then
  keeps the *original* `$CTX` already present in the view scope, so the partials run with an undefined
  `$CTX['filters']` (warnings, empty filters, no products). Assign it explicitly
  (`$CTX = $__L['CTX'] ?? $CTX;`) before extracting, and `unset($__L['CTX'], $__L['PAGE'])` so the
  by-reference `$PAGE` is not clobbered.
* **Never cache the form/sidebar element in a JS variable.** `var form = document.querySelector('[data-filter-form]')`
  captured at load points at a **detached node** as soon as the fragment endpoint swaps the markup: the
  first tick works, every later tick re-submits the *old* values and the page appears to ignore clicks
  (symptom: "adding a second filter does nothing, the URL never changes"). Look the element up inside the
  handler every time — and if you replace the sidebar at all, keep the DOM nodes of the ticked inputs alive
  (see §5a).
* **A big `str.replace()` that eats a line range can duplicate a header.** Rewriting a view by slicing
  index→index left the old data-prep block above the new one; it still parsed, but the page rendered
  nonsense. After surgery on a view, `php -l` **and** read the assembled region back before moving on.

## Verification

* `scripts/mobile-overflow-check.mjs` (no npm deps, CDP over the Playwright Chromium) — measures
  `scrollWidth` vs `clientWidth`, lists every element crossing the right edge, and with
  `--selector ".ship-table"` reports whether a wide table switched to the stacked-card layout. Run it at
  360/390/414 px on the category, product, cart/order and any price-table page.
* Diff facet groups per category after changing rules (`grep` the rendered sidebar for `fgroup-title`).
* Spot-check that the top-5 facet values for a category are plausible; a value like `1 inch` on 19-inch
  racks or `4 Gbit` on LTE routers means a rule needs a bound or a suffix.
* Confirm chips round-trip: select two brands + one spec value, then assert the result count drops and
  both chips link back to a URL that removes exactly one filter.
